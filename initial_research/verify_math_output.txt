3. MoE CLAIM — '64 experts x 4M, top-2 => 32x savings'
==========================================================================
total expert params  : 256M
active expert params : 8M
ratio                : 32x  -> README arithmetic is CORRECT

BUT the README presents this as system savings. It is not:
  - MEMORY is unchanged: all 256M must be resident or streamable.
  - attention/router/embeddings/norms are NOT reduced.
  - Amdahl: if experts are 60% of FLOPs, 32x on that part gives
      expert share 50% -> end-to-end 1.94x
      expert share 60% -> end-to-end 2.39x
      expert share 70% -> end-to-end 3.11x
      expert share 80% -> end-to-end 4.44x

5. CAN 1e12 PARAMETERS EVEN BE STORED?
==========================================================================
format               bytes/param          size   fits 256GB SSD?
FP16                      2.0000     2000.0 GB                NO
INT8                      1.0000     1000.0 GB                NO
INT4                      0.5000      500.0 GB                NO
2-bit packed              0.2500      250.0 GB                NO
ternary 5-per-8bit        0.2000      200.0 GB                NO
1-bit                     0.1250      125.0 GB               yes

NOTE: ternary is 5 values per byte (3^5=243<=256) -> 1.6 bits/param, not 1.58.
      1e12 ternary params = 200.0 GB.
      Base Mac mini ships 256 GB SSD. After macOS (~20 GB) you have ~215 GB.
      => 1T ternary params fits ONLY on the 256GB model with almost nothing
         else on disk. 512 GB internal or external NVMe is the sane config.

6. DECODE ROOFLINE — what throughput is physically available?
==========================================================================
Resident-in-RAM case (no SSD traffic), ternary 0.2 B/param:
   active params   bytes/token   tok/s @84GB/s  tok/s @102GB/s
          0.5B       0.10 GB           840.0          1020.0
          1.0B       0.20 GB           420.0           510.0
          2.0B       0.40 GB           210.0           255.0
          5.0B       1.00 GB            84.0           102.0
         10.0B       2.00 GB            42.0            51.0
         32.0B       6.40 GB            13.1            15.9

Kimi K2 reference point (1T total / 32B active), if it were ternary:
  32B active x 0.2 B = 6.40 GB of weights per token
  That 6.40 GB would fit the 9.66 GB budget IF it were the same
  6.40 GB every token. It is not: the active set is re-selected per token
  from a 200 GB pool, of which only ~6.5 GB (3.2%) is resident.
  Coarse-grained routing (8 of 384 experts) gives poor reuse, so most of
  the 6.40 GB is fetched from SSD each token:
    fully-missing case : 2.13 s/token = 0.47 tok/s
    50% hit rate     : 1.07 s/token = 0.94 tok/s
    80% hit rate     : 0.43 s/token = 2.34 tok/s
    90% hit rate     : 0.21 s/token = 4.69 tok/s
  => even at a 90% hit rate K2 gives ~4.7 tok/s. Porting K2 is NOT the answer;
     the activation set must be made far smaller AND far more reusable.

8. PRODUCT-KEY MEMORY — why 1e12 params is tractable at all
==========================================================================
PEER/product-key: N slots addressed by two sqrt(N) sub-key sets.
Index cost is O(sqrt(N)*d), NOT O(N*d). This is the whole unlock.

  N=     1e+06 slots: sqrt(N)=     1000  key params=    2.0M (   4.1 MB fp16)  value params=    2.0B
  N=     1e+08 slots: sqrt(N)=    10000  key params=   20.5M (  41.0 MB fp16)  value params=  204.8B
  N=     5e+08 slots: sqrt(N)=    21817  key params=   44.7M (  89.4 MB fp16)  value params=  974.8B
  N=     1e+09 slots: sqrt(N)=    31623  key params=   64.8M ( 129.5 MB fp16)  value params= 2048.0B

Target: 476M slots x d=2048 = 974B value params
  value store on disk @ ternary: 194.8 GB
  key index in RAM @ fp16      : 89.3 MB  <-- fits trivially

Per token, top-k=128 over 8 memory layers:
  value bytes fetched : 419.4 KB   (bandwidth: negligible)
  random reads        : 1024
    @ 100K IOPS -> 10.24 ms/token (98 tok/s ceiling)
    @ 300K IOPS -> 3.41 ms/token (293 tok/s ceiling)
    @ 500K IOPS -> 2.05 ms/token (488 tok/s ceiling)
  => memory layers are IOPS-bound, not bandwidth-bound. 4KB-align slots.

11. WRITING vs TRAINING MEMORY — the actual path to 1e12
==========================================================================
Regime (a) GRADIENT-TRAIN the memory values (Memory Layers at Scale style).
    1 tok/param -> C=5.69e+24 FLOP -> 1.37e+05 years
   20 tok/param -> C=1.14e+26 FLOP -> 2.73e+06 years
   VERDICT: DEAD. Off by 5-6 orders of magnitude. Not a scheduling problem.

Regime (b) WRITE the memory values by encoding a corpus once (RETRO/kNN-LM style).
   Cost = 2 * N_encoder * corpus_tokens (forward pass only, one epoch).
   Need 476M slots. corpus_tokens = slots * chunk_len.

     encoder  chunk   corpus tok       FLOP    wall clock
        10M     64     3.04e+10   6.09e+17        5.3 d  <-- viable
        10M    128     6.09e+10   1.22e+18       10.7 d  <-- viable
        10M    256     1.22e+11   2.44e+18       21.4 d  <-- viable
        30M     64     3.04e+10   1.83e+18       16.0 d  <-- viable
        30M    128     6.09e+10   3.65e+18       32.0 d  <-- viable
        30M    256     1.22e+11   7.31e+18       64.1 d
       100M     64     3.04e+10   6.09e+18       53.4 d
       100M    128     6.09e+10   1.22e+19      106.8 d
       100M    256     1.22e+11   2.44e+19      213.5 d
       500M     64     3.04e+10   3.04e+19      266.9 d
       500M    128     6.09e+10   6.09e+19      533.8 d
       500M    256     1.22e+11   1.22e+20     1067.6 d

   CORRECTION TO MY OWN EARLIER LINE: at a 500M encoder and 256-token chunks
   this is 4489 days (12.3 years), NOT 'weeks'. The job is only feasible with
   a SMALL encoder and SHORT chunks. Concretely:
     encoder 10M params, 64-token chunks -> 30.4B corpus tokens -> 5.3 days one-time
   The Neural Engine (38 TOPS INT8) could cut this ~3-10x further if the
   encoder can be compiled to it, but treat that as UNVERIFIED upside.

Regime (c) what the corpus requirement implies:
   chunk= 64 -> need   30.4B tokens of text  (the Pile ~300B, FineWeb ~15T -> available)
   chunk=128 -> need   60.9B tokens of text  (the Pile ~300B, FineWeb ~15T -> available)
   chunk=256 -> need  121.8B tokens of text  (the Pile ~300B, FineWeb ~15T -> available)

=> CONCLUSION: 1e12 parameters is reachable on this box ONLY because ~97% of
   them are WRITTEN (one forward pass each) rather than TRAINED (many backward
   passes each). That is a ~2-week batch job vs a ~10^5-year one.
